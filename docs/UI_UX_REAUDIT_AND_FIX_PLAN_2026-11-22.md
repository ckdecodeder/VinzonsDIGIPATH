# Vinzons DigiPath desktop UI/UX re-audit and repair plan

22 November 2026 · Assessment baseline on local `main` at `4dac99c318ea622c63d0a277d79131a862e88d63`

**23 November implementation update.** The seven batches covering F01–F17 have been implemented locally. The dated findings below describe the original assessment. The [changelog](../CHANGELOG.md) records the passing tests, desktop verification, recovery details and outstanding staff and equipment checks.

**Repair record identity and custody first.** A public tracking dialog showed the number of one claim slip above the subject of another. An Office clerk following a pending receipt alert landed on a generic list. A preview placed a record at the Mayor’s Office while its own location field named Records Office. These are the most consequential failures of the interface’s promise to tell a person which document they are looking at, who holds it, and what they can do next.

The current design already gives staff a recognizable municipal workspace. The seal, blue and teal palette, task-specific sidebar, explicit receipt actions, and persistent registration footer are worth retaining. The strongest visual opportunity is to give the tracking number, recorded holder and next permitted action a consistent reading order across entry points.

## Prioritized findings

P0 means a demonstrated system-wide blocker requiring immediate intervention. P1 covers incorrect records, custody or official output, unintended writes, and blocked core work. P2 covers misleading summaries, substantial accessibility or navigation friction, and repeated operational confusion. P3 covers clarity and visual improvements with a working route through the task. **17 findings: 8 P1, 6 P2 and 3 P3. No P0 was established.**

## Detailed repair plan

### Batch 1 · Keep public lookups and receipt alerts attached to the right record

**Deliver F01 and F02 first.** These changes can be developed in parallel. Both should land with tests that control the timing of requests.

1. In public tracking, keep the editable input, last submitted number and last verified result separate. Scope every request to its submitted number. Abort or ignore earlier responses, including interval callbacks. Stop polling when the result is no longer being viewed. Show the returned number alongside the subject, holder and last successful check. During a refresh, keep the verified result visible with a refreshing or stale state.
2. In notifications, resolve a transmission reference to its permitted document and enter the existing focused Documents route. Carry the exact receipt where relevant. On success close the dock and focus the record heading or available receipt action. If access changed, explain what happened and let the user dismiss the reminder. Scope local dismissal storage to the account, handle legacy shared entries conservatively, and keep read acknowledgement independent from physical receipt.
3. **Accept** when A and B return in both orders and every displayed field belongs to one submitted number. Try a failed refresh, rapid edits, closed dialog and tracking link from a claim slip. For Office and Reception, open a custody receipt, a copy receipt, an already-received item and an unavailable item. Admin/Mayor can inspect a visible delivery with only their permitted actions. Changing accounts on the same browser preserves each user’s pending alerts.

### Batch 2 · Make scan retakes and cancellation target one operation

**Deliver F03 and F04 together with the scanner UI and API owners.** Identify the saved capture and command IDs before changing labels. A bare document ID on a retake currently means append, so that alone cannot implement replacement.

1. Separate **Retake pages**, **Add a page** and **Start another document**. Keep the original saved intake, tracking number, page order and metadata while a replacement batch is captured. Show how many pages will be replaced. Commit the replacement only after every page is ready and acknowledged. Keep the previous pages available if capture or save fails. Repeated confirmations must converge on one result.
2. Device Management should distinguish loading, unavailable, unconfigured, known offline and online states. Bind editable configuration and command actions to an identified, loaded device. A known offline device may still have editable metadata under existing rules. Add an explicit setup path if setting up a new device is intended. A placeholder used for display must never become the write target.
3. Target scan cancellation by device and command ID, with a server-side check for the expected command type and cancellable state. Keep an executing operation distinguishable from a confirmed stop. If a broader administrative cancel operation is needed, give it separate explicit scope and count. Continue observing the original command after a failed cancel request.
4. **Accept** with isolated storage and a simulated device. Retake one page and several pages, fail halfway, abandon a retake and retry after a lost acknowledgement. Verify one record, stable tracking, correct page order and preserved originals. With a scan plus unrelated queued work, cancel only the intended scan. While device data is pending or failed, confirm zero write requests. Reserve physical capture, sorting and stop confirmation for operator acceptance.

### Batch 3 · Align document detail, custody and action recovery

**Deliver F05 and F06.** The full-record handoff summary and existing submission gate are starting points.

1. Derive the holder, pending custody recipient, copy recipients and next permitted action from the same facts for preview, full record and Reception. Replace fixed Mayor/FIFO text with the observed office and state. Render unknown custody explicitly. Keep the preview compact, with one visible Open record action.
2. Submit notes, signing, acknowledgement and rejection through an in-flight guard. Keep the exact draft and dialog on failure. On success, close once and update the record. For an ambiguous response, read back the outcome before enabling another action. Put the error beside the action and restore focus to a useful control.
3. **Accept** with a direct-office document, a Mayor-required document, one primary recipient plus two copies, and a copy received while custody remains pending. All entry points must agree on the holder. Double Enter must emit one request. A slow save must keep the note visible. A failed or uncertain request must preserve typed text and avoid a duplicate history entry.

### Batch 4 · Correct dates and restore original downloads

**Deliver F07 and F08.** Original-download repair can ship independently. Coordinate calendar changes between frontend and backend so list, report and export filters agree.

1. Treat date-only values as municipal calendar dates. Convert instants to `Asia/Manila` before deriving a day. Reuse the existing Manila date helper where appropriate. For the log API, turn inclusive calendar inputs into a start instant and an exclusive following-midnight instant. Keep historical date-only records intact. Display a time only when the source provides an instant. Validate reversed ranges at input and action boundaries and give an inline correction.
2. In Archive Details, use the existing authenticated original downloader. Give the button the filename in its accessible name. Show pending, expired-session, denied and missing-file feedback in context. Keep direct handling for supported inline legacy originals. Use the verified backend for managed media.
3. **Accept** with 23:59, 00:00, 00:30 and 08:00 Manila fixtures under Manila and another browser timezone. Registration, scans, archive date, search, Activity Logs and report coverage must agree. Test a single day, an open-ended interval and a reversed range. Reversed dates block generation with a correction. Download synthetic PDF and JPEG originals from Archives, compare bytes and filenames, then exercise missing-file and expired-session recovery.

### Batch 5 · Reconcile dashboards and directory counts

**Deliver F09 and F10.** Reuse the workflow/status helpers already used by Documents. Use the same visible dataset for a number and its drill-down.

1. Include Completed, returned and supported legacy states in summaries. Represent unexpected historical states explicitly so totals reconcile. Point the Office Archived tile to its authorized Archived-filtered documents. Preserve priority rank zero when sorting recent documents. Separate a loaded-empty result from a still-loading or failed status/activity panel.
2. Define an incoming delivery separately from an acknowledged receipt. Choose an explicit label for each displayed count. Pass per-source readiness into Offices and Document Types. For Archives, wait for the document join before declaring zero matches. Show available fields while dependent sections load, and allow Retry on the failed part.
3. **Accept** with one record per status, a completed-only set, an older urgent record, one pending and one acknowledged transfer, and one office with five staff. Check every tile count against its destination for each role. Stall each required source separately, then fail and retry it. Zero should appear only after a complete count. Keep already loaded records and independent actions usable.

### Batch 6 · Make desktop controls and text consistently usable

**Deliver F11–F14.** Do the common desktop interaction work first, then the scanner and separately packaged WiFi portal.

1. Provide a visible-on-focus skip link and a stable main heading target. On intentional page changes, place focus where the user can begin work. Preserve focus inside active dialogs and during background refresh. Give repeated row actions a record-specific name. Complete Reports’ tab behavior with a labelled panel, one tab stop, arrow keys, Home and End, or adopt ordinary category buttons with a consistent selected-state announcement.
2. Bring archive dates/IDs, report labels, staff counts and device statuses to at least the documented 12 px metadata size. Let text wrap, use tabular numerals where helpful, and preserve the space for action buttons. Provide distinct disabled and busy treatments for the shared primary button in both themes. Keep the explanation next to offline Capture. Label the hardcoded heartbeat JSON as an example and tuck connection instructions below live state and recovery.
3. Set explicit foreground and background pairs for WiFi choices, expose the selected network and announce scan/connection progress and errors. Keep manual SSID entry available. Update both Pi source copies through the normal packaging workflow.
4. **Accept** with keyboard-only public lookup, sidebar to Documents, Reports category switching, directory search, dialog close and focus restoration. Check high zoom on desktop, forced colors, reduced motion and a screen reader. Verify computed metadata sizes at both desktop widths and inspect long identifiers and office names. Verify at least 4.5:1 for active WiFi text in default and selected states, plus visible keyboard focus. Distinguish offline, busy and available scanner actions in both themes.

### Batch 7 · Improve the first screen and everyday feedback

**Deliver F15–F17 after the record and accessibility fixes.** Validate these design choices with task walkthroughs.

1. Give the public page two clearly named entry points, **Track a document** and **Staff sign-in**. Put a labelled Track button beside the claim-slip field. Keep one concise instruction, preserve direct tracking links, and retain the municipal seal at a size that leaves both tasks prominent on a laptop.
2. Let the home queue take the height its rows need within a useful upper bound. On laptop widths, give the activity destination room to wrap or move supplementary activity below the queue. Name a feed of transfers accordingly. Let a transfer row open its relevant record or filtered activity, while View all opens the full permitted activity view. Check sparse and busy queues.
3. Use the signed-in role’s scope in the Activity heading and description. Add a true empty state and a separate Clear search action in Users. Use a single nonblocking confirmation for a successful profile save, while retaining inline, focused errors for failures.
4. **Accept** by asking a first-time resident to track a claim slip and an employee to sign in without prompting. Have a clerk identify both endpoints of a recent transfer on a 1366-wide desktop. Check that one successful profile save produces one announcement and that a search miss offers a one-action recovery. Record observations and revise copy or layout if either audience hesitates.

## Verification and release handoff

- **At each batch** add a focused regression for the observed failure, rerun the dashboard suite and production build, and record the revision and evidence in the changelog. Batches changing command scope, attachment handling or calendar filtering also need the applicable isolated API/storage tests. Preserve existing role restrictions, data readiness behavior, modal focus and draft recovery throughout.
- **Before publication** run the resident lookup and four signed-in role walks with synthetic data, then obtain staff desktop acceptance on the target system. Record failures separately for UI, network, permissions and physical equipment. Coordinate any release, backups and rollback with the existing performance/deployment plan. Do not use a retake fix to deduplicate historical records automatically.
- **Recovery** should be per batch. UI-only adjustments can be reverted independently. Ship compatible client/server contracts for command targeting, page replacement and date filtering. Exercise interrupted replacement and recovery on disposable storage before operator testing. Publication and historical-record repair are separate decisions.
- **Local audit evidence** is available in `backend/pgdata/ui-reaudit-20261122/`. `results.json` contains synthetic results, `sheet.png` gives the visual index, and individual PNGs preserve the browser observations. This directory is ignored by Git. The findings and acceptance examples above are self-contained for reviewers on other checkouts.
