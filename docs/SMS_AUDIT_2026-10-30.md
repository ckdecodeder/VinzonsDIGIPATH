## Findings

### SMS-01 — P1: API acceptance is recorded as successful SMS sending

**Locations:** `backend/utils/senderNotifications.js:136–152,293–298`; `dashboard/src/pages/DocumentList.jsx:1540`.

The adapter checks only `response.ok`, ignores the response ID/state, and immediately stores `Sent` with `sentAt`. The phone can accept a message into its queue and later fail because of SIM, signal, permission, balance, or Android errors. DigiPath never reads subsequent status and disables retry once marked `Sent`. Even an unrelated HTTP 200 response at a misconfigured private endpoint is treated as success.

The provider distinguishes pending submission, Android processing, SMSC acceptance, and recipient delivery. Delivery reports must be requested to establish recipient confirmation. See the official [status lifecycle](https://docs.sms-gate.app/features/status-tracking/).

**Evidence:** The SMS-01 probe returns an HTTP 202 response whose unread body describes `Pending`. DigiPath stores `Sent`, sets `sentAt`, and retains no gateway message ID. This reproduces local classification behavior; no phone failure was induced.

**Proposed repair:** Persist a gateway correlation ID and an `Accepted`/pending state. Reconcile with bounded polling or authenticated status events supported by the installed local gateway version. Use `Sent` only after the appropriate provider confirmation; show `Delivered` only when independently reported. Validate a bounded response schema and discard sensitive response fields.

### SMS-02 — P1: ambiguous sends can duplicate; interrupted sends have no recovery path

**Locations:** `backend/utils/senderNotifications.js:142–147,244–257,272–298`; `backend/routes/notifications.js:128–130`.

After a request reaches the phone, its response can be lost. Every timeout/transport error becomes `Failed` and eligible for another POST. Requests contain no stable message ID, so a manual retry can enqueue the same SMS again. The single-in-flight claim protects overlapping sends while the row remains `Sending`; it cannot establish whether an earlier request was accepted.

Conversely, a process crash after the claim, or a persistence failure after provider acceptance, leaves `Sending`. There is no status reconciliation or operator recovery path for that state. Blindly resetting it to `Failed` would reintroduce duplication risk.

**Evidence:** One probe simulates acceptance followed by a lost response: two attempts create two submissions without an ID. Another injects failure while persisting `Sent`: the row remains `Sending`, and another attempt returns no claim. These are synthetic ambiguity/persistence cases, not evidence of two real SMS deliveries.

**Proposed repair:** Persist a stable provider message ID before submission, verify duplicate-ID semantics against the installed gateway, reconcile unknown outcomes, and distinguish definite rejection from ambiguous transmission. Add recoverable claims/leases, but reconcile the provider before resubmitting. The provider recommends unique IDs and expiry controls in its [sending guidance](https://docs.sms-gate.app/features/sending-messages/).

### SMS-03 — P1: resends ignore withdrawn consent and corrected contact details

**Locations:** `backend/routes/notifications.js:120–130`; `backend/utils/senderNotifications.js:305`.

New notifications check `notifySender` and `senderNotificationConsent`. Resends check only document visibility, channel, provider mode, status, and attempts. The current document returned by `assertCanAccessDocument` is discarded. A saved queued/failed message can therefore be sent after consent is disabled, SMS is deselected, or the contact has been corrected; it still targets its old saved recipient.

**Evidence:** The real resend handler, loaded with mocked authorization/document/storage/provider dependencies, returns success and submits the saved recipient even when the current document has both notification flags false and a different contact number. This does not test real authentication or SQL permissions.

**Proposed repair:** Recheck current consent, notification selection, and normalized recipient when claiming delivery, including previously queued rows. Cancel/suppress obsolete rows. A contact change should invalidate old-recipient messages and require an explicit new message; do not silently redirect a historical message to a new person. Coordinate the check with document edits to avoid a consent race.

### SMS-04 — P1: a committed workflow event can permanently lose its notification

**Locations:** `backend/routes/documents.js:586–597,624–630`; `backend/utils/senderNotifications.js:321–350`; `backend/routes/archives.js:38–50`.

Document/workflow commits finish before the sender-notification row is saved. A crash in that gap leaves no queued event. If saving the outbox row fails, `queueSenderNotifications` logs an error and returns `[]`; document operations can still succeed. There is no durable pending event, unique event key, or general replay mechanism. The edit-time zero-outbox fallback is not a replacement for the missed routing, approval, receipt, or archive event.

**Evidence:** Source shows the post-commit ordering. A synthetic outbox-save failure is swallowed, returns an empty result, and creates no row. The probe does not reproduce a real PostgreSQL commit/crash.

**Proposed repair:** Create an outbox event in the same transaction as the workflow mutation. Deliver after commit through a bounded worker. Use a unique workflow-event/channel/recipient key so replay is safe. Do not put network SMS calls inside document transactions.

### SMS-05 — P2: SMS gateway waits can make successful document routing appear to fail

**Locations:** `backend/routes/transmissions.js:155–174`; `backend/routes/documents.js:122–147`; `backend/utils/senderNotifications.js:342–343`; `dashboard/src/api/documentService.js:106–110`.

Routing creates one sender message per destination and awaits each provider call sequentially before returning the API response. Seven destinations can consume about 70 seconds with the default 10-second provider timeout, or 210 seconds at the allowed 30-second setting, plus other work. The dashboard defaults to a 60-second write deadline. A slow reachable gateway can therefore make the browser report failure after routing has already committed. Users may repeat an action whose first attempt succeeded.

**Evidence:** Source review and deadline arithmetic; this is a conditional failure mode, not a measured live delay or load test.

**Proposed repair:** Return after the document mutation and durable outbox commit. Let a separately bounded worker send messages, with deliberate per-phone pacing. Consider a single route summary instead of one SMS per office, while preserving event history.

### SMS-06 — P2: the five-attempt limit and attempt counter are not atomic

**Locations:** `backend/routes/notifications.js:121–130`; `backend/utils/senderNotifications.js:244–253`.

The route checks a snapshot before acquiring the delivery claim. The claim does not check the current attempt count and writes `snapshot.deliveryAttempts + 1`. If two requests read count four, the first can fail before the second claims. Both send and both write count five. The status lock prevents simultaneous in-flight calls, but not sequential claims using stale snapshots; it also loses accurate attempt history.

**Evidence:** Two stale fourth-attempt snapshots produce two mocked provider submissions and leave the stored count at five. This models the interleaving in memory, not PostgreSQL scheduling.

**Proposed repair:** Check the current count and increment it under the same row lock as the status claim. Preserve current metadata rather than copying a stale snapshot. Use a retry cooldown and record each attempt without storing credentials/provider bodies.

### SMS-07 — P2: the dashboard silently hides older queued or failed messages

**Locations:** `backend/routes/notifications.js:108–117`; `dashboard/src/api/documentService.js:171,285–293,436`; `dashboard/src/pages/DocumentList.jsx:272–276,1529–1553`.

The global endpoint returns only the newest 250 notifications, without pagination metadata. Document details filter this same global array. Once a document's messages fall outside that window, its modal can say no updates were queued and provide no retry control for existing failures. A document-specific backend endpoint exists but is not used by this client.

**Evidence:** Source trace across endpoint, collection service, and modal. No live records or rendered production screen were inspected.

**Proposed repair:** Load document-specific notification history when opening details, and paginate the global outbox with explicit total/has-more state and status filters. Distinguish empty results from failed or incomplete loading.

### SMS-08 — P2: unsupported numbers are accepted at intake and become unrecoverable stale outbox recipients

**Locations:** `dashboard/src/pages/ReceptionistDashboard.jsx:610–615`; `backend/routes/documents.js:373–401`; `backend/routes/devices.js:257–261`; `backend/utils/senderNotifications.js:8–15,310–343`.

The reception UI says international `+` numbers are accepted, while the adapter supports only Philippine mobile numbers. Intake and queueing do not apply that validator. Invalid or unsupported SMS recipients are persisted as queued rows and fail only when actual delivery is attempted. Errors collapse to a generic connectivity/configuration message, and correcting the document does not update the saved recipient used by retry.

**Evidence:** A synthetic international recipient is queued successfully in outbox mode, then rejected by the provider's number validator. Source review establishes the UI mismatch and absence of shared intake validation. No real intake/API request was submitted.

**Proposed repair:** Share Philippine mobile normalization/validation between intake, updates, and queueing when SMS is selected. Preserve other contact information separately if needed. Show a field-specific error and invalidate stale queued recipients after correction. Validate notification flags as booleans rather than coercing strings such as `"false"` to true.

## Other operational observations

- Plain HTTP is accepted and used by the setup example, so gateway Basic credentials and SMS content travel without transport encryption. A private IPv4 restriction prevents arbitrary public destinations; it does not encrypt traffic. Use a trusted isolated network and, where supported, authenticated TLS termination. Do not expose the phone port publicly. No network interception test was performed.
- The message builder has no length or SMS segment budget. A synthetic 2,000-character detail remains over 2,000 characters after formatting. Subjects, office labels, and action notes can create multipart texts. Set a concise template/segment budget and a per-phone sending rate before activation. The provider documents automatic message splitting in its [sending guide](https://docs.sms-gate.app/features/sending-messages/).
- There is no DigiPath phone health/status screen or general queue worker. A phone outage will need operator attention. Android background survival and health checks are deployment acceptance items; the provider's [local-server FAQ](https://docs.sms-gate.app/faq/local-server/) describes those constraints.
- Some operation-plan text still describes the superseded Twilio path. Reconcile that wording when implementing the selected Android repairs so operators have one current setup path.

## Existing protections verified or observed

- Outbox is the default; switching provider does not automatically flush historical rows.
- SMS requests use Basic authentication, one normalized Philippine mobile recipient, a private numeric IPv4 destination, rejected redirects, and a bounded timeout.
- Provider response bodies are not copied into stored errors. The present implementation also discards useful response ID/state, covered by SMS-01.
- Retry routes require authentication, Admin/Receptionist role, and document visibility in source. The synthetic handler probe deliberately substitutes authorization and does not establish real role acceptance.
- The claim uses the model's transactional row lock to exclude a second claim while status is `Sending`. Existing mocked overlap tests pass; a real SQL SMS-claim race test was not run.
- Consent flags are respected when creating new notifications. They are not rechecked on retry (SMS-03).

2. Move sending out of document requests; add recipient validation, document-specific history, operator errors, queue pacing, expiry, and message limits.
